# Manager workspace

The desktop application now uses a site workspace with seven sections. Existing site profiles, vaults, release-integrity checks and deployment engines are retained. This change does not introduce Worker domain service accounts or hostname support for VM endpoints.

New sites have empty server addresses, App URL and management-PC IPv4. Grey documentation-range examples are separate visual hints; they are never entry values and cannot be saved or used for connections. Existing profiles retain their configured addresses. The main window, custom dialogs, nested windows and future Tk dialogs use the shared ProdCast icon; Windows process identity is set to ProdCast Manager.

The default desktop now recreates the earlier WebEngine preview's light shell, sidebar, grouped cards, conditional access fields, four-step deployment wizard and in-page settings tabs using styled Tkinter/ttk. It uses neither Qt nor a browser. No HTML, JavaScript, WebChannel, WebView2 or Chromium renderer is required. The shared DesktopController and Python deployment engines retain the same profile, vault, release validation and operation contracts.

The single-file EXE bundles Tcl/Tk and the Python engine. It does not need browser/GPU initialization, a renderer helper or a separately installed GUI runtime. Root and popup windows use ProdCast branding. Initial administrator credentials remain viewable while an operation runs, without saving/revalidating the profile. Onefile packaging still uses a small extraction/cleanup parent and the application process; two Manager processes are normal.

Builds use `release/manager.spec` and explicitly exclude PySide/PyQt/shiboken. `release/check_tk_ui.py` exercises the real controls, verifies that the frozen archive contains Tk and no Qt/browser runtime, and can capture only its own test window for visual review. `build.ps1` runs controller/engine tests and the packaged Tk smoke test with a timeout. Existing workflow version stamping and one-EXE artifact naming continue to apply.

## Everyday use

Tk controls preserve English/Russian language support, grey non-value examples, encrypted access storage, explicit fingerprint confirmation and operation recovery safeguards. Count changes require explicit −/+ clicks; mouse-wheel events over comboboxes scroll the page rather than changing values. Add/install/repair/remove worker buttons remain visible; unsupported actions are disabled with an explanation. Selecting a server scrolls its access editor into view.

- **Overview:** current local site, local deployment receipt, unresolved journal count and links to status checks. Remote health is never inferred from a completed local operation.
- **Servers & workers:** a visible table shows every server's role, IPv4, SSH user, access method and fingerprint status (scrollable for large topologies). Select a row to edit its access below; this is not a server dropdown. Edited addresses update the overview immediately. Password shows the SSH password directly, SSH key shows private key and optional passphrase. Linux adds explicit sudo choices; Windows does not. Fingerprint verification is separate, asynchronous and requires explicit trust. Test selected server checks sign-in and privileges without staging an agent or requiring other hosts to be configured.
- **Install / update:** Site → Package → AI → Review. The expected hash is the SHA256 of `release-manifest.json`, not of the ZIP. Local package verification does not bypass the engine's final compatibility and ownership checks. Update can intentionally omit AI packages using Keep existing AI; installation still follows the site's AI setting and release requirements.
- **AI:** separate runtime/model package selection and retry action. Core package selection is shared with Install / update. The deprecated GPU-driver installation option is not exposed; its legacy profile field remains readable for compatibility only.
- **App settings:** general/network settings, HTTPS import/deployment, domain login, activation. Domain-login connection, lookup and user tests are separate tabs. LDAP without TLS has its acknowledgement beside the transport choice. Successful tests do not mean settings are deployed or that container trust matches VM trust.
- **Backups & recovery:** server snapshots, encrypted portable export, data restore, Manager-profile recovery, component repair and full reset have distinct descriptions. Portable archive forms keep path, password and confirmation together. Existing engine checks still validate archive identity/compatibility before restore.
- **Operations:** a real history list includes core installation/update, Worker, AI, certificate, checks and maintenance runs. The current operation opens automatically. All targets is the default; target and summary filters are available. Full combined logs, selection copying, follow-output control and log-folder access remain available. App administrator access stays in the header and remains read-only during operations.

## Saving and recovery

`Save draft` stores incomplete non-secret inputs as `ui-draft.json`; it does not replace the validated `site.json` or deploy anything. Passwords must be saved with **Save server access**. Explicitly emptying a previously loaded secret clears it; changing authentication methods does not erase the alternate method's session draft. Before leaving a modified site, Save / Discard / Cancel is offered.

New local operation records are stored in `prodcast-data/logs/operations`. They are diagnostic records, separate from deployment ownership journals. Their `finished` status means the local action returned, not a live health verdict. A run left `running` after restarting Manager is displayed as interrupted/unknown. Earlier Manager logs remain available in the logs folder; they are not retroactively attributed to individual actions or sites.

Full log means the Manager event log plus the redacted remote diagnostic excerpts collected on action failures. It does not claim to stream every server transcript continuously. Captured App/DB/Worker/AI diagnostic excerpts appear under the relevant target filter; the original diagnostic files also remain in the logs folder.

All six existing journal families are inspected, including unreadable files. Recovery instructions identify the action that must be repeated. The existing stop action supports core/AI ownership release; it does not claim to cancel Worker, certificate or maintenance transactions. Those journals remain visible and require their supported resume path. Stopping is not rollback.

After successful core deployment, `ui-deployed.json` records the release, manifest and a keyed settings signature. It contains no credentials. It permits comparison of saved App settings with the last successful deployment. Existing profiles without a receipt show **unknown**. The receipt is not a substitute for remote health inspection.

An installed, topology-bound profile cannot silently become a new site by editing its core address or ID. Use New site. Uninstalled local profiles retain the existing separate-profile behavior when endpoints change. Existing worker IDs remain stable across removal and re-addition; initial worker count is for new sites, with explicit Add / Remove for installed sites.

Completed Worker removals are authoritative over older UI drafts and stale open-window submissions. Drafts carry a saved-membership stamp; reconciliation removes only the same address/role proven removed by a completed Worker action whose target matches the saved roster. Unrelated edits and package selections remain intact, and repaired legacy drafts are archived in history. The UI switches away from a deleted selection; update guards remain active for unauthorized address/roster edits. New explicit re-add drafts carry the current stamp and are not erased. Removed Workers are pruned from component receipts; older receipts containing vault-confirmed retired roles no longer block the next update. No service, installation ID or vault secret is reset by draft reconciliation.

## Validation

### AI preservation and reconnect

An already installed AI (successful AI journal or encrypted installed receipt) is preserved during core updates even if its inclusion checkbox was cleared. Manager keeps AI enabled in the effective/saved profile and skips AI packages in that case. "Keep existing AI" preserves the connection, models and runtime; it is not an instruction to disable integration. Sites with no installed AI can still omit it.

If a completed core update recorded AI disabled, enable App connection to AI on the **AI** tab and run its AI action. When an existing AI installation is recorded, Manager checks all owners, preserves the old journal, restores only the scoped PostgreSQL access rule/firewall, reloads PostgreSQL (no DB restart), verifies existing AI readiness, patches App's AI enable/URL values using its existing credentials, and verifies from App. No Worker action or model/package upload occurs. App backend services may restart briefly; env changes roll back if restart fails. Failures retain a resumable AI journal and do not mark the core deployment failed. First-time AI installation or pending package installation still uses the normal package path with the required connection steps. DB component receipts now include the AI-enabled setting because DB access depends on it.

### Existing installation and scoped updates

Overview → **Verify existing installation** uses the exact complete release and manifest from the current/failed core journal. It checks every core VM, ownership, running services, App scheduler and readiness, runtime identity and Worker configuration. It never starts, reinstalls or changes service accounts. Only after every check passes does it archive the original journal and reconcile installation metadata. AI can then be installed separately, or a new release selected for update. A missing/unhealthy service is reported rather than silently marked complete.

Healthcheck is optional, not an update prerequisite. Older profiles without component receipts use the traditional full-stack update (App, DB and all Workers), with credential checks before stopping services and normal compatibility/ownership/resume protections. Successful update creates receipts for subsequent scoped updates. An interrupted traditional operation follows its existing resume/stop rules, not a mandatory healthcheck.

Successful deployment or reconciliation saves encrypted per-component receipts. **Preview changed services** compares the selected release and saved settings against these receipts, or shows all core groups for a legacy profile. With receipts, updates stop/configure/install only changed service groups: App, DB and each Worker. Worker-only updates temporarily drain/resume only the selected Workers' consumers, without restarting App. App-only updates leave Worker services and their logon accounts alone. Shared dependency/settings changes can legitimately include more than one group. Backups and original-operation resume checks still apply.

App updates retain a database backup before schema migrations even when the DB service itself is unchanged. This backup does not restart or reconfigure DB. Dependencies and migrations are visible in the preview; component isolation is not a promise of zero shared-data access.

Backups preserve application data rather than reinstallable Worker environments. Traditional and scoped updates, and manual server backups, no longer archive Worker installation directories. An old pending Worker backup action returns an explicit skipped receipt. Existing Worker backups and previous runtime directories are retained. DB backups before App migrations remain mandatory. App server backups and portable exports exclude the top-level media directories `models_files/` and `official_models/`; workflow scripts/notebooks/signatures, uploaded external-source files and all other App media remain included. Model metadata remains in the database, so users must restore models separately or reimport them from SMB. AI model-cache exclusions remain in place.

New `.pcbackup` archives use recovery schema 2 with `media_scope=application-data-without-models-v1`. Restore preserves existing model directories while replacing the backed-up App media; archives declaring this scope cannot contain model-directory entries. The encrypted framing and manifest checks remain unchanged. New Manager versions still read schema-1 archives with their original full-media restore semantics. Older Managers reject schema 2 rather than accidentally deleting model directories. Backup/restore screens and operation logs explain these exclusions. Runtime state, original release/installation identity and secret checks remain required for restore.

Worker update stops always query live service/process state, including on retries; stop receipts are not cached. The owned service stays Disabled throughout backup and replacement so SCM recovery cannot restart the old runtime. Manager checks tracked process identities (PID plus creation time), refuses replacement while processes survive, and rechecks immediately before deleting the old registration. The prepared target is enabled for startup only after configuration, and its previous startup mode is restored after readiness. A failed installation with an update stop receipt stops the owned runtime again. If this operation durably recorded the fully configured pending target, its exact service registration and required files still match, failure recovery leaves it stopped with Manual startup. Incomplete, foreign or stale targets remain disabled. Retry automatically enables the prepared target and reapplies explicitly configured credentials; no manual enable is required, including for services disabled by older Manager builds. The original startup mode and same-operation journal remain available until readiness succeeds. New installations retain the packaged startup defaults. Existing stopped-state receipts from older Manager builds are revalidated.

Servers → select Worker → **Worker Windows service account (not SSH)** supports preserving its current account (default), a dedicated local/domain account, or explicitly returning to local `prodcast-managed`. Passwords are encrypted separately from SSH and omitted from drafts/public state/logs. Saving settings does not change a running service. Replacement requiring the existing account's password stops before any service mutation if credentials are missing. Preflight checks credential availability; it does not attempt a separate `LogonUser` login. Windows Service Control Manager authenticates the supplied credentials when the configured service starts. Manager requires the service to be Running and Worker isolation/TLS readiness to pass before committing installation. Startup failures retain the original error and log the configured service account/state for diagnosis. Both administrator and non-administrator custom accounts are accepted. IT must grant effective service-logon rights. Manager does not join the domain, override domain policy, or add accounts to Administrators. The auto-provisioned managed account remains non-administrator. Healthcheck accepts an already-running, manually configured service without reapplying its account.

A component update that failed during preflight can accept corrected account settings and recalculate its scope using the same release. Manager archives the previous journal, updates the sealed settings, and repeats all remote checks. This applies only while phase is `preflight`, no completed update steps exist, and no action is recorded in flight. Before the first update action, Manager durably records `applying` and the in-flight action; from then on the original settings and scope remain mandatory, including when that very first action fails. Other releases and installation identities remain blocked.

### Local journal replacement and desktop instances

Worker update diagnostics record the selected account mode and whether credentials are present, used for replacement registration, reapplied through Windows service configuration, or preserved. Password values are never logged. Before startup and after readiness, the transcript records the configured account, resolved SID (or unresolved), service state/start mode, PID and service exit codes. On failure it records the exception chain's numeric Windows codes and up to 12 matching Service Control Manager events from the current startup attempt, examining at most 256 provider events. Event matching uses service/display-name fields rather than unrelated text matches. Unavailable or delayed event records are explicitly reported; diagnostic failures do not replace the original error. These diagnostics are read-only: they do not probe account logon or change local/domain rights. They appear in the existing Worker operation transcript and downloaded install diagnostics; no separate log collection is required. A zero service exit code alone is not proof of successful logon.

Only one desktop Manager can open a given portable `prodcast-data` directory at a time. A second launch exits before loading profile journals; the OS releases the instance lock when the owning process closes/crashes. Separate data directories remain independent, and existing deployment-operation locks still prevent concurrent CLI/GUI mutations on a profile.

Local JSON saves use unique temporary files in the destination directory, flush/close them, then atomically replace the existing file. Readers in desktop snapshots and pending/history views share delete access on Windows and coordinate with same-process writers. Per-file cross-process locks serialize writers. Transient replacement errors are retried for a bounded interval. Persistent access denial retains both the prior valid journal and the complete pending temporary file and reports their paths. Manager never deletes the old journal first, truncates it in place, disables endpoint protection, or bypasses NTFS permissions. Ordinary reads/writes/deletes of unrelated files do not establish that Windows permits replacing a particular open journal.

LDAP and LDAPS both allow the search account and password to be omitted together. App deployment keeps the existing user-bind contract and group restrictions. Without a search account, directory diagnostics require temporary test-user credentials; these are never saved and anonymous lookup is not attempted. Clearing the search account also removes its encrypted saved password. LDAP without TLS still requires explicit acknowledgement; LDAPS certificate verification remains mandatory.

Regression coverage includes both authentication methods, saved password retention, trusted-key confirmation, Linux privilege selection, incomplete drafts without secrets, legacy profile separation, stable Worker IDs, explicit AI omission, persistent operation history, target filtering (including errors), concurrent log append, interrupted/corrupt records, all pending-journal families, deployment receipts, bilingual labels and directory test-result handling. Deployment-engine tests remain part of the full suite.
